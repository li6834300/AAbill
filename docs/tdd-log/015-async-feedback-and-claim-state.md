# 015 — 异步等待反馈与认领提交状态

## 验收标准

- Given Owner 已选择发票,When AI 正在识别,Then 页面显示醒目的阻断式处理界面,并说明多页发票可能需要较长时间。
- Given 用户在校对/分享/认领页发起需要服务器响应的操作,When 请求尚未完成,Then 页面显示等待层并阻止重复操作;后台轮询不打断用户。
- Given Printed totals 已显示,Then “更新并重新校验”是低层级次要动作,不会抢过上传、分享等主流程。
- Given Participant 已提交认领且未修改,Then 提交按钮禁用并变灰;修改数量或清空旧认领后重新可用。

## 红

- `BlockingWaitOverlay.test.tsx`:等待层隐藏、普通通讯等待、AI 专属醒目状态。
- `claim-draft.test.ts`:服务端认领与本地草稿相同、增减、清空、均摊商品忽略。

两组测试先因组件与比较函数不存在而失败。

## 绿

- 新增跨 Web/iOS/Android 的阻断式等待层,AI 模式使用更高视觉层级。
- Owner 页所有既有 `run` 远端操作统一接入等待层;Participant 的进入、拍照识别、提交也接入,5 秒轮询维持静默。
- 认领草稿改为逐项对比 `myPortion`,提交后未修改时按钮为灰色;同时修复“清空全部旧认领无法提交”和记住口令后未恢复已有认领的问题。
- Printed totals 按钮改成右对齐的紧凑次要按钮,文案明确为重新检查。

## 重构

- 等待界面抽成 `BlockingWaitOverlay`,避免各页面各自维护遮罩样式。
- 认领变更判断抽成纯函数 `hasClaimChanges`,便于覆盖边界情况。

## 视觉系统合并后的回归补强

- 红:`Button.test.tsx` 证明禁用主按钮仍是半透明品牌绿,不符合“已提交且未修改时变灰”的验收标准。
- 绿:填充按钮禁用后统一使用中性灰面、灰边与灰字;认领提交按钮沿用既有 `dirty` 判定,因此提交成功且未改动时呈真正灰色。
- Printed totals 的“更新并重新校验”改为紧凑 ghost 动作,移除整行绿色主按钮视觉,并保留明确的重新校验文案。
- Owner 账单首次读取也使用阻断等待层;读取失败时切换为错误说明,不会留下永久遮罩。
